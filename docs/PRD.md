# TripSplit 旅游分账 Agent — 产品需求文档 (PRD) v1.0

> 状态：已实现（`tripsplit/`）。本文既是需求，也是验收依据；"实现备注"标注与代码对应的位置。

## 1. 背景与目标

多人自由行的 AA 记账有四个反复出现的痛点：

| 痛点 | 现状 | 本产品的回应 |
|---|---|---|
| 消费记录分散 | 微信群聊、支付截图、口头约定混在一起，事后凑不齐 | 文字 / 截图 / 语音统一录入，字段自动抽取 |
| 垫付关系复杂 | 谁替谁付了、付了几次，人工算容易错 | 账本结构化存储 + 最少转账结算 |
| 参与人易记错 | "那顿饭小林没去"这类信息常被漏掉 | 参与人作为一等字段，缺失即追问；核账 Agent 体检 |
| 结算核对繁琐 | 结算前要翻完所有记录找错 | 模糊描述检索历史账目；Agent 自动核账并给出可确认的修改建议 |

**目标用户**：小团体（2–8 人）自由行中负责记账的"管账人"。

**产品目标**：
1. 单笔消费从"发生"到"入账"≤ 10 秒（文字/截图/语音任一路径）。
2. 结算前找错的时间从"翻完整本账"降到"确认 Agent 给出的几条建议"。
3. AI 不替用户改账：所有写操作由用户确认，且每笔修改可追溯。

**非目标**：多设备同步、多人协同编辑、汇率换算、与支付平台直连。

## 2. 用户动线与产品边界

管账人核心场景（一趟旅行的生命周期）：

```
创建旅行 ──► 消费录入 ──► 账本管理 ──► 核账 ──► 结算
  成员/日期    文字/截图/语音   编辑/筛选/     Agent 体检    最少转账
               自动入账或追问   待补全/审计    确认建议      复制到群
                                   ▲
                               查询（RAG）：模糊描述定位旧账 / 报告
```

**产品边界**：
- 数据只存在管账人的浏览器（localStorage）。服务端三个 AI 接口（`/api/extract`、`/api/search`+`/api/report`、`/api/reconcile`）只接收账本快照，不持久化、不回写。
- AI 的输出一律是"建议"：录入是草稿（自动入账可一键撤销），检索与核账给出字段级修改预览，用户确认后才写入。

## 3. 页面与交互

### 3.1 首页 `/`
- 旅行卡片列表：名称、日期、成员、已确认合计、笔数、待补全角标。
- 「创建旅行」：名称、成员（逗号分隔，第一位为管账人本人，录入时"我"指向他）、起止日期。
- 校验：名称必填；≥2 位成员；成员名不重复；结束日期不早于开始日期。
- 「重置为示例数据」：载入内置示例旅行（含故意埋的异常，便于演示核账）。

### 3.2 旅行页 `/trip/[id]?tab=`
五个标签：录入 / 账本 / 查询 / 核账 / 结算。账本标签带待补全数量角标。

#### 录入
- 三种方式切换：文字、支付截图（可附说明）、语音（浏览器 Web Speech API 转写为文字，音频不上传）。
- 点「解析并入账」→ 展示四项字段置信度条（金额 / 付款人 / 参与人 / 分类）。
- 结果三种状态：
  - **已自动入账**：展示入账卡片，提供「撤销」「继续记下一笔」。
  - **需要补全**：列出追问（≤3 条）；用户可 (a) 一句话补充后重新解析（携带上一轮结果），(b) 手动补全（缺失字段高亮），(c) 先存为待补全。
  - **未识别为消费**：说明原因，引导换截图或改用文字。
- 「最近录入」展示最近 3 笔。

#### 账本
- 按天分组，组头显示当日合计；筛选：全部 / 待补全 / 按成员（付款或参与）。
- 卡片：时间、备注、分类、来源徽标（文字/截图/语音）、待补全徽标、低置信徽标、付款人 → 参与人、金额。
- 点击卡片进入编辑：金额、分类、付款人（单选）、参与分摊（多选 + 全员）、备注、时间；可删除（二次确认）。编辑待补全项时缺失字段高亮；保存后状态变为已确认、置信度置 1。展示原始证据（文字/转写/截图缩略图）。
- 「手动记一笔」同一表单。
- 「修改记录」：每次新增/修改/删除的审计条目，标注来源（用户 / Agent 建议·已确认 / 检索建议·已确认）。

#### 查询
- 自然语言输入 + 示例问题。
- 回答区：意图徽标（找账 / 改账 / 统计）、条件已放宽提示、回答正文、解析出的结构化条件、置信度。
- **证据引用**：回答引用的账目以高亮卡片列出。
- **修改预览**：当用户意图是改账时，逐字段 before → after，「确认修改 / 确认删除」或「忽略」。
- 检索候选（可展开）：分数、命中的结构化条件、文档文本，用于调试与讲解。
- 「生成报告」：按分类 / 按天 / 谁垫付三张表 + 模型写的标题、要点、小结。

#### 核账
- 「开始核账」→ 结论摘要 + 用量（轮次、工具调用次数、token）。
- 每条 finding：严重度（高/中/低）、类型（重复录入 / 参与人 / 付款人 / 金额异常 / 待补全 / 日期 / 其他）、标题、证据、建议、涉及账目卡片、可选的修改预览（确认/忽略）。
- 「Agent 执行轨迹」：Planning 文本、每次工具调用的名称/入参/回传/耗时，按顺序展示。

#### 结算
- 待补全提醒（未计入结算）。
- 每人已垫付 / 应分摊 / 净额表，合计与人均。
- 最少转账方案列表 + 「复制到群里」。

## 4. 业务规则

### 4.1 数据模型
- `Trip`：id、name、currency、members[]（id, name）、startDate、endDate、selfMemberId。
- `Expense`：id、tripId、amount、currency、payerId、participantIds[]、shares?（权重，缺省均摊）、category（餐饮/交通/住宿/门票/购物/娱乐/其他）、note、occurredAt、source（manual/text/image/voice/agent）、confidence（0–1）、status（pending/confirmed）、evidence（kind、text、thumbnail）。
- `AuditEntry`：action（create/update/delete）、origin（user / agent-confirmed / search-confirmed）、summary、before/after。

### 4.2 分摊与结算（`lib/settle.ts`）
- 每笔按参与人权重分摊，四舍五入到分，余数归最后一位参与人，保证各人份额之和等于金额。
- 付款人不在参与人内则不分摊（允许"请客"），但核账会提示。
- 只有 `confirmed` 的账目计入余额；`pending` 不计入，结算页提示。
- 净额 = 已垫付 − 应分摊。转账方案：债务人、债权人各按金额降序贪心配对，转账笔数 ≤ 成员数 − 1。

### 4.3 多模态录入决策（`lib/extract/extract.ts`）
- 模型输出每个关键字段 + 置信度，并给出追问；人名用成员名，服务端解析为 id（精确 → 包含 → 去"小/阿/老"前缀）。
- 自动入账阈值：金额 ≥ 0.8、付款人 ≥ 0.7、参与人 ≥ 0.7，三项同时达标才自动入账；否则 `ask`。分类置信度不触发追问（可事后改）。
- 付款人解析不到成员 / 参与人为空 → 对应置信度记 0 → 必追问。
- 截图不能证明付款人：默认当前使用者，置信度 ≤ 0.75（若 ≥ 0.7 仍可自动入账，但账本标注来源与置信度，核账会复核低置信项）。
- 模型判定 `is_expense=false` → `reject`，不入账。
- 补充回答携带上一轮输出，模型在其基础上修正，补充优先级最高。

### 4.4 检索与报告（`lib/search/`、`lib/report.ts`）
- 两段式：① 模糊描述 → 结构化条件（日期区间、金额区间、付款人、参与人、分类、关键词扩展、意图）；② 结构化条件硬过滤 → TF-IDF（中文字二元组）余弦排序取前 8 → 模型基于候选作答。
- 过滤为空时放宽为纯语义检索并在 UI 标注"条件已放宽"。
- 回答的引用只能来自候选；服务端过滤非法 id。修改建议只在用户明确要改/删时产生，且只含要改的字段。
- 报告的所有数字来自确定性聚合，模型只做叙述；提示词禁止自行计算。

### 4.5 核账 Agent（`lib/agent/`）
- 链路：系统提示词封装（目标、工作方式、优先级、成员 id 对照）→ 模型先写 Planning → 循环调用只读工具（get_trip / list_expenses / get_expense / find_duplicates / check_integrity / category_stats / get_balances）→ 工具结果以 tool_result 回传 → 以 `submit_findings`（strict schema）提交结构化结论，循环结束。
- 上限 12 轮；没有工具调用就结束的轮次会被提示继续；`submit_findings` 结构不合法时作为错误回传让模型重提。
- 规范化：引用不存在账目的 finding 过滤其 id；修改建议中的成员 id 必须有效；空 patch 丢弃。
- **安全边界**：服务端没有写接口；工具全部是对快照的纯函数；建议 → 预览 → 用户确认 → 客户端写入 → 审计记录。

## 5. 异常处理

| 场景 | 处理 |
|---|---|
| API key 缺失 / 无效 | 500，文案"服务端未配置有效的 ANTHROPIC_API_KEY" |
| 限流 | 429，"请求太频繁，请稍后再试" |
| 网络不通 | 502，"无法连接模型服务" |
| 模型输出不符合结构 | 500，"模型输出不符合结构"；用户可重试 |
| 模型拒绝（refusal） | 500，"模型拒绝处理该输入" |
| 输出被截断（max_tokens） | 核账返回"输出被截断，请重试" |
| 核账超过 12 轮 | "核账轮次超限，请重试" |
| 截图不是支付凭证 / 文字不是消费 | `reject`，不入账，给出原因 |
| 语音识别不可用 / 麦克风被拒 | 禁用按钮并提示改用 Chrome/Safari 或直接输入文字 |
| 检索条件过滤为空 | 放宽为语义检索并标注 |
| 回答引用了不存在的账目 | 服务端过滤 |
| 建议涉及的账目已被删除 | 预览显示"该账目已不存在" |
| localStorage 写入失败（配额） | console 告警，内存态仍可用；截图只存 360px 缩略图 |
| 待补全账目 | 不计入余额；结算页与账本角标提醒 |

## 6. 验收标准

**录入**
- [ ] 文字"阿强付的火锅 412，大家 AA"→ 自动入账，付款人阿强、参与人全员、金额 412、分类餐饮。
- [ ] 文字"火锅 412"（无付款人/参与人）→ 需要补全，追问含付款人与参与人；补充"我付的，四个人"后自动入账。
- [ ] 支付截图 → 金额与商户正确；付款人默认当前使用者且置信 ≤ 0.75。
- [ ] 风景照 → 未识别为消费，不入账。
- [ ] 自动入账后「撤销」能删除该笔并写入审计。

**账本**
- [ ] 按天分组合计正确；筛选"待补全"只显示 pending。
- [ ] 编辑待补全项补齐金额与参与人后状态变为已确认。
- [ ] 每次新增/修改/删除都有审计条目且来源正确。

**查询**
- [ ] "第一天晚上那顿火锅是谁付的" → 回答含阿强、412，并引用对应账目卡片。
- [ ] "小林付的超过 300 的账" → 解析出付款人+金额下限，候选只含满足条件的账目。
- [ ] "把钟水饺那笔的参与人改成大家" → 给出修改预览，确认后账本更新且审计来源为"检索建议·已确认"；忽略则不变。
- [ ] 生成报告的分类合计 = 账本已确认合计。

**核账（示例数据）**
- [ ] 发现：火锅重复录入、钟水饺付款人不在参与人内、农家菜参与人为空、包车 3500 疑似多打一个零（证据原文 350）、机场早餐待补全。
- [ ] 每条 finding 有证据与建议；修改预览逐字段展示；确认后生效，忽略不变。
- [ ] 执行轨迹可见 Planning 与每次工具调用。
- [ ] 核账过程不改变账本（未确认前账本 hash 不变）。

**结算**
- [ ] 净额之和为 0（参与人非空时）；转账笔数 ≤ 成员数 − 1；按方案转账后所有人净额归零。
- [ ] 有待补全时显示提醒。

**工程**
- [ ] `npm test` 通过；`npm run build` 通过；API key 不出现在前端 bundle。

## 7. v2 功能增量（2026-11-04）

在 v1 四件事之上补齐以下能力。每项给出规则与验收标准；页面位置见括号。

### 7.1 多人协作与云同步（旅行页 ⋯ → 邀请同行者）
- 无账号体系：分享码即凭证；邀请链接 `/join/<code>`，落地页选择"我是谁"或新增成员。
- 合并规则：账目按 `updatedAt` 最后写入胜；删除为墓碑（墓碑时间 ≥ 修改时间则删除胜，不复活）；旅行文档整体后推胜；审计按 id 去重只增。
- 客户端：本机变更 800ms 防抖推送全量账目 + 删除 id；每 8s 轮询、回前台立即拉取；离线时标记并在联网后推送。拉取合并时保留本机比服务端更新的版本与上次同步后新建的账目。
- 验收：两台设备各记一笔，10s 内双方都能看到两笔；A 删除、B 同时修改同一笔，最终以墓碑为准；无 `TRIPSPLIT_DB_URL` 时入口提示未配置，其他功能不受影响。

### 7.2 分摊规则扩展（记一笔 / 编辑消费）
- 四种方式：均摊、按份数、按比例（合计 100）、指定金额（未指定者分剩余）；余数分到分并归最后一位参与人。
- 请客：勾选后付款人自动移出参与人且不可勾回；核账 Agent 对 `treat=true` 不再报"付款人不在参与人内"；录入解析识别"请客/我请/X 请大家"。
- 验收：`npm test` 覆盖四种方式与请客；百分比不等于 100、指定金额超总额时表单拒绝保存并提示。

### 7.3 多币种与汇率（记一笔：币种下拉）
- 账目保留原币金额与 `rate`（1 外币 = ? 本币）；结算、预算、报告一律按本币折算。
- 汇率按消费日自动取欧洲央行参考汇率（`/api/rate`，frankfurter.dev），周末回退最近交易日；取不到或币种不支持时手填。录入解析识别日元/美元等并输出 ISO 代码。
- 验收：JPY 3000、rate 0.048 两人分，各 72；卡片显示原币与 ≈ 本币。

### 7.4 预算与消费趋势（账本顶部）
- 总预算 + 分类预算；进度条 85% 转黄、超支转红并在首页卡提示；展开看分类进度与按天柱图（单系列、本币、悬停显示金额与笔数、日均预算参考线、表格视图）。
- 验收：设总预算 5000 后示例账本显示超支金额；无预算时显示"设个预算"入口。

### 7.5 还款跟踪与锁账（结算）
- 每笔转账可"已转"，剩余方案按扣除已转后的净额重新计算；已转列表可撤销；"还没转的人"汇总 + 一键复制催款文案。
- 全部结清后可锁定账本：增删改账目被拒并提示解锁；解锁保留已转记录。
- 验收：标记一笔已转后剩余笔数减少且合计守恒；锁定后"记一笔"弹出提示且不写入。

### 7.6 分享与导出
- 结算：生成图片卡片（Canvas → PNG），支持系统分享或下载。账本：导出 CSV（带 BOM，Excel 直接打开）。报告：打印友好页面另存为 PDF。
- 验收：CSV 含币种、汇率、本币金额、分摊方式、请客、来源、证据列；PDF 含小结、统计、收支、转账、明细。

### 7.7 批量导入（录入页 → 批量导入）
- 多张截图：并发 2 逐张走 `/api/extract`；账单 CSV：支付宝（GBK）/ 微信（UTF-8）解析支出明细，按行程日期筛选后由模型分类（`/api/import` rows 模式）；订单文本：模型抽取多笔（text 模式）。
- 草稿列表：与账本及批内自动查重（复用 `find_duplicates`），重复项取消勾选；缺字段项入账后标待补全；模型判定无关项默认不勾选；每条可展开表单修改。一次入账产生一条审计。
- 验收：导入含重复行的账单，重复项被标出且默认不入账；订单文本"2 间房"抽出 1 条金额正确的草稿。

### 7.8 语音升级（录入页语音模式）
- 配置 `STT_API_KEY` 时走 MediaRecorder 录音 → `/api/transcribe`（Whisper 兼容），Safari / 微信可用；未配置退回 Web Speech。
- 离线或识别失败的录音进 IndexedDB 队列；联网后"处理 N 条离线录音"逐条识别 + 解析，auto 直接入账、其余存待补全并带转写证据。
- 验收：断网录音后队列计数 +1；联网处理后账本出现对应账目。

### 7.9 核账 Agent 进化（核账页）
- 忽略建议时可写理由并选择落为"本次旅行规则"或"长期习惯"；两者随快照上送，系统提示词里分别作为"不要再报的情况"和"判断依据"；长期习惯同时喂给录入解析与批量导入。
- 结算前自动核账：账本指纹（id+updatedAt）与上次核账不同时，结算页顶部提示"先核账"，跳转后自动运行。
- "Agent 记忆"面板可手动增删规则与习惯。
- 验收：对"付款人不在参与人内"忽略并记为规则后，重新核账不再出现该条；改一笔账后结算页出现提示。

### 7.10 自动导入消费
- 不接邮箱 / 平台账号（需平台授权）；以 7.7 的账单 CSV 与订单文本粘贴作为落地方式，Agent 生成草稿、人工确认。

### 7.11 评测与可观测
- `eval/cases.json` 20 例录入解析用例（含请客、外币、追问、拒绝），`npm run eval` 按决策 / 金额 / 付款人 / 参与人 / 分类 / 请客算准确率与成本，结果写 `eval/results/` 与 `evals` 表。首轮基线：20 例通过 18，字段准确率 100%，决策 90%（两例为"推断付款人/参与人该不该追问"的标注边界）。
- 每次模型调用记录路由、耗时、token、成本估算、成功与否到 `runs` 表（无库时进程内存）；`/admin` 按路由汇总 p50/p90、成功率、成本，并列出评测历史；`ADMIN_TOKEN` 控制访问。
